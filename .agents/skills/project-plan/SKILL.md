# 프로젝트 작업 계획

## 입력
사용자의 새 요청, 실제 저장소 구조와 기존 계획, 프로젝트 규칙·제안서·결정 기록, `docs/testing.md`.

## 절차
모든 프로젝트 경로는 이 스킬이 속한 저장소 루트를 기준으로 한다. 루트의 `AGENTS.md`, `proposal.md`, `docs/project-brief.md`, `docs/workflow.md`, `docs/decisions/README.md`와 필요한 ADR을 읽는다. 아래 경로가 없으면 없는 상태를 보고하고 구현됐다고 추정하지 않는다.
확정 초기 정책은 영어 가상 기사·한국어 보고서·로컬 JSON·프로젝트 .venv + pip이며 API 미연결이다. 기존 확정 결정을 다시 묻거나 새 결정을 개인 대신 확정하지 않는다.

1. 요청이 초기 하네스인지 향후 앱 기능인지 구분하고, 제안서 §3.1의 5개 국가·지역 수집 및 3개 출처 비교 목표와 충돌하는지 확인한다. 현재 앱 기능 구현은 별도 요청 전 범위 밖이다.
2. 실제 파일을 읽고 영향 파일, 작업 순서, 필요한 문서 갱신, 기존 검사 및 추가할 검사 계획을 정리한다. `src/`, `tests/`, `data/fixtures/`는 실제 존재 여부를 확인한다.
3. `docs/testing.md`에 등록된 검사를 검증 방법으로 연결한다. 명령이 미구성이면 미구성으로 적고 P4 구성을 선행 조건으로 제시한다. 아직 없는 명령이나 실행 증거를 만들지 않는다.
4. 스택·저장/데이터 정책·범위 변경, 비용, 실제 API 연결 등 중요 결정이 필요하면 선택지·장단점·추천 근거를 제시하고 개인 답변을 기다린다. 무관한 미정까지 질문하지 않는다.
5. `workspace/plan.md`에 요청 요약, 범위/제외 범위, 영향 파일, 순서, 검증 방법, 문서 갱신, 결정 상태와 질문을 기록한다. 기존 기록이 있으면 실행 번호·날짜를 붙여 보존한다. 원문 사용자 입력 대신 필요한 요약만 기록한다.

## 산출물
`workspace/plan.md` 및 필요한 개인 질문. 계획 작성은 구현·검사 성공의 증거가 아니다.

## 수정 범위와 중단 조건
계획 기록만 작성하며 앱 코드·테스트·환경·확정 ADR은 수정하지 않는다. 중요 결정에 답이 없으면 의존 작업은 보류하고 질문 후 멈춘다. 필요한 문서가 없거나 충돌하면 확인 가능한 계획과 차단 이유를 기록하고 멈춘다. 계획 작성이 끝나면 구현을 시작하지 않는다.
