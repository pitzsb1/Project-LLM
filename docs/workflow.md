# 개인과 AI의 작업 절차

작성일: 2026-10-28. 현재 P5 절차 직접 수행 이후 project-check·project-docs 명시 호출 수행 및 초기 검사 재통과. project-plan 명시 호출·다른 세션의 자동 발견·개인 회고·최종 채택은 미확인. 근거는 docs/skill-status.md와 workspace의 실행 2 기록이다. 한 Codex 대화에서 역할을 순서대로 전환하며 개인이 흐름을 관리한다.

## 책임
| 역할 | 입력 | 출력 | 수정 범위 |
|---|---|---|---|
| 개인 | 제안서, 선택지, 계획, 검사·리뷰 결과 | 중요 결정 답변, 진행 요청, 최종 채택 | 프로젝트 목표·중요 정책 결정 |
| 작성자(AI) | 요청, AGENTS.md, 개요·ADR·테스트 계획 | 계획, 허용 범위의 변경, 변경 요약 | 요청으로 허용된 파일. 현재는 문서, P4는 최소 개발 기반 |
| 검사자(AI) | 실제 변경, docs/testing.md | 명령·종료 코드·출력 요약·판정 | 검사 기록만. 코드·테스트·통과 기준 수정 금지 |
| 검토자(AI) | 요청·규칙·diff·검사 증거 | 근거가 있는 리뷰와 보완 항목 | 리뷰 기록만. 코드·테스트 수정 금지 |

역할 전환은 독립적인 검증 환경을 보장하지 않는다. 검토자는 작성자의 주장보다 실제 파일과 실행 증거를 확인한다. 이번 흐름은 별도 서브에이전트를 사용하지 않는다.

## 실행 순서
1. 요청 확인: 제안서, 규칙, 기존 파일·결정을 읽고 단계와 범위를 확인한다.
2. 영향과 계획: 영향 파일·순서·검증 방법·미정을 `workspace/plan.md`에 정리한다(project-plan 스킬 실행 시 사용).
3. 중요 결정 확인: decisions/README.md 기준에 해당하면 선택지·근거를 제시하고 개인 답변을 기다린다. 미확정 ADR은 제안/보류로 남긴다. 일상적인 수정에는 별도 승인을 요구하지 않는다.
4. 작업: 작성자가 허용된 변경을 수행하고 변경 요약을 남긴다. 이번 과제는 앱 기능을 구현하지 않는다.
5. 검사·검토: 검사자는 testing.md에 등록된 실제 검사를 실행해 `workspace/checks.md`에 남긴다. 검토자는 diff·실행 증거·범위 준수를 확인하고 `workspace/review.md`에 통과/수정 필요/판정 불가와 근거를 적는다.
6. 문서 갱신: 실제 변경에 맞춰 해당 기준 문서를 수정하고 `workspace/docs-update.md`에 파일·이유·남은 질문을 적는다.
7. 개인 채택: 변경·리뷰·미정을 제시한다. 개인이 결과를 확인하고 최종 채택한다. AI가 개인 채택을 대신 기록하지 않는다.

P4 초기 구성 기록은 `workspace/bootstrap-log.md`, P5 최종 하네스 점검은 `workspace/harness-review.md`에 남긴다. P4 bootstrap-log는 실제 기록이며 P5에서는 계획·검사·문서 갱신·최종 점검을 기록한다. 개별 파일의 존재와 최신 판정은 실제 파일을 확인한다.

## 실패·재시도·중단
최초 작업의 검사·검토가 실패하면 구체적 원인을 작성자에게 넘긴다. 추가 수정은 최대 2회이며 개인이 횟수를 관리하고 AI도 기록한다. 매 수정 후 필요한 검사를 다시 수행한다.
2회 추가 수정 후에도 실패하면 현재 상태·명령·실패 원인·미검증 범위·다음 조치를 기록하고 중단한다. 검사 기준을 완화하거나 실패를 성공으로 바꾸지 않는다. 권한·외부 환경 문제도 미실행 또는 실패로 구분한다.

## 기록과 권한
원본 실행 로그·사용자 입력·실제 기사 전문은 Git에서 제외한다. 과제 증거용 요약은 키·개인정보·원문을 제거해 별도 파일로 제공할 수 있으며 실제 실행 사실을 보존한다. `.gitignore`는 P4에서 구성했다. workspace의 허용된 Markdown은 민감 정보가 없는 요약 전용이다.
AGENTS.md와 workflow는 지침이며 도구 권한을 강제하지 않는다. 실제 샌드박스·권한 설정에 따라 승인이나 작업 위치 조정이 필요할 수 있다.
